# Карта проекта

## 1. Назначение этой карты

Этот файл — практическая карта проекта для сопровождающего разработчика и GPT/Codex.
Она помогает быстро понять текущую структуру MVP, зоны ответственности слоёв и
поток выполнения приложения без чтения каждого файла перед началом работы.

Это не README, не полный справочник API, не список задач, не журнал изменений и не
руководство по рабочему процессу Codex. Для локального запуска сначала см. `README.md`;
для принятого контекста MVP — `docs/PROJECT_CONTEXT.md`; для политики провайдера —
`docs/LLM_MODEL_POLICY.md`.

## 2. Текущее состояние MVP

Текущий проект — приватный локальный MVP с приоритетом серверной части. Он содержит
серверную часть на FastAPI, статический веб-интерфейс по адресу `/app`, загрузку
документов с ориентацией прежде всего на изображения, создание задач обработки,
статус/историю, рабочий процесс извлечения, рабочую область результата,
предпросмотр исходного файла, экспорт Markdown/PDF, удаление и вызываемую функцию
очистки по сроку хранения.

Стандартный локальный режим использует детерминированный провайдер `fake`.
Режим реального провайдера через OpenRouter и подготовка медиа через ImgBB существуют,
но включаются явно и требуют соответствующей конфигурации и секретов.
Промышленное развёртывание, аутентификация, изоляция нескольких пользователей,
биллинг и очистка по расписанию не заявлены.

Экспорт PDF поддерживается. Извлечение данных из PDF на входе не следует
документировать как гарантированную возможность: интерфейс принимает `.pdf`, но
серверный путь извлечения по-прежнему основан на диагностике изображений и Pillow.

## 4. Конфигурация и правила работы приложения

Настройки во время работы находятся в `src/document_digitization_ai/core/config.py`
и загружаются из окружения / локального `.env` через pydantic-settings.
`.env.example` — безопасный шаблон, хранящийся в репозитории; настоящий `.env`,
API-ключи и локальные учётные данные коммитить нельзя.

Важные текущие значения по умолчанию из `.env.example`:

| Область | Текущая настройка |
| --- | --- |
| Провайдер | `EXTRACTION_PROVIDER=fake` |
| OpenRouter | `OPENROUTER_API_KEY=change_me`, `OPENROUTER_MODEL=change_me` |
| Структурированный вывод | `LLM_STRUCTURED_OUTPUTS_ENABLED=true`, `LLM_PROVIDER_SCHEMA_MODE=compact` |
| База данных | `DATABASE_URL=sqlite+aiosqlite:///./data/app.db` |
| Хранилище | `STORAGE_UPLOADS_DIR=./data/uploads`, `STORAGE_RESULTS_DIR=./data/results` |
| Срок хранения | `ARTIFACT_RETENTION_DAYS=7` |
| Подготовка медиа | `MEDIA_STAGING_BACKEND=none`, `IMGBB_API_KEY=change_me` |
| Жёсткое ограничение загрузки | `IMAGE_DIAGNOSTICS_MAX_FILE_SIZE_BYTES=20971520` |

Границы политики:

- Стандартный локальный сценарий должен оставаться автономным от сети и использовать `fake`.
- Реальные вызовы OpenRouter требуют настоящего API-ключа OpenRouter и модели без значений-заглушек.
- `MEDIA_STAGING_BACKEND=imgbb` требует `IMGBB_API_KEY` и отправляет байты изображения документа в ImgBB.
- Для визуального извлечения через OpenRouter требуется доступный провайдеру медиафайл с `PUBLIC_URL`.
- Вывод провайдера считается недоверенным, пока его не примет серверная валидация.
- Скрытого перехода с неудачно настроенного `openrouter` на `fake` нет.
- Сгенерированные во время работы данные должны находиться в игнорируемых корневых каталогах хранилища, например `data/`.

## 6. Основной пользовательский сценарий

1. Пользователь открывает `/app`.
2. Пользователь загружает через веб-интерфейс документ, ориентированный прежде всего на обработку как изображения.
3. Серверная часть создаёт задачу и сохраняет артефакт исходного загруженного файла.
4. Рабочий процесс извлечения выполняет диагностику, подготовку медиа, вызов провайдера и серверную валидацию.
5. Интерфейс периодически запрашивает статус задачи и обновляет состояние истории/рабочей области.
6. Результат появляется в рабочей области, когда задача достигает состояния готового результата.
7. Пользователь просматривает сводку, предупреждения, значения, значения, производные от таблиц, таблицы, текст и Markdown.
8. Пользователь скачивает Markdown или PDF, сформированные серверным кодом экспорта.
9. Пользователь просматривает исходный файл или удаляет задачу из текущего представления/истории.

## 7. Поток серверной части / API

`create_app()` связывает настройки и `DocumentProcessingFacade` с состоянием приложения
FastAPI, инициализирует локальную базу данных во время жизненного цикла, если приложение
владеет фасадом, регистрирует маршрутизаторы документов/задач и подключает статический
веб-интерфейс.

Группы HTTP-маршрутов:

- `GET /health` — ответ о работоспособности приложения.
- `POST /documents` — проверка загрузки и создание задачи через фасад.
- `GET /jobs` — история задач с фильтрацией по `limit` / `offset` / `status`.
- `GET /jobs/{job_id}` — подробности задачи, попытки и представления перечня артефактов.
- `GET /jobs/{job_id}/status` — периодический запрос статуса.
- `GET /jobs/{job_id}/result` — проверенные данные результата вместе с данными для проверки/представления.
- `GET /jobs/{job_id}/markdown` — формирование Markdown без записи артефакта.
- `POST /jobs/{job_id}/markdown/export` — формирование и запись артефакта экспорта Markdown.
- `GET /jobs/{job_id}/pdf` — возврат сгенерированных байтов PDF.
- `GET /jobs/{job_id}/preview` — безопасный предпросмотр/скачивание исходного загруженного файла.
- `DELETE /jobs/{job_id}` — удаление состояния из БД и безопасных деревьев хранилища.
- `GET /jobs/{job_id}/artifacts` — перечень метаданных ссылок на артефакты, а не скачивание произвольного содержимого сохранённых артефактов.

Маршруты API являются адаптерами. Они разбирают HTTP-ввод, вызывают фасад,
преобразуют объекты представления в модели ответов Pydantic и отображают серверные
ошибки в безопасные HTTP-ошибки.

## 8. Путь извлечения / провайдера / подготовки медиа

Рабочий процесс извлечения принадлежит серверной части:

1. Сохранить исходный загруженный файл в настроенном корневом каталоге загрузок.
2. Выполнить детерминированную диагностику изображения с помощью Pillow.
3. Построить входной контекст провайдера из сохранённых данных задачи и настроек.
4. Подготовить медиа через настроенный порт подготовки медиа.
5. Построить пакет промпта и пакет схемы.
6. Вызвать настроенного провайдера извлечения.
7. Сохранить необработанные/очищенные артефакты провайдера для внутреннего и отладочного использования.
8. Валидировать и нормализовать вывод провайдера во внутренние контракты.
9. Сохранить принятый результат извлечения и переходы состояния.

Режимы провайдера:

- `fake` — детерминированный локальный провайдер для стандартных локальных запусков и автоматизированных тестов.
- `openrouter` — явно включаемый адаптер реального провайдера. Импорт OpenAI SDK изолирован в
  `src/document_digitization_ai/extraction/openrouter.py`.

Подготовка медиа:

- `MEDIA_STAGING_BACKEND=none` возвращает ссылку на локальный файл и не выполняет внешнюю загрузку.
- `MEDIA_STAGING_BACKEND=imgbb` отправляет байты изображения в ImgBB и возвращает доступный провайдеру публичный URL.

Контракт промпта/схемы:

- Версия пакета промпта: `extraction_prompt_v0`.
- Целевая версия схемы: `extraction_result_v0`.
- Режимы схемы: `compact` и `full`.
- Адаптер OpenRouter требует структурированный вывод и формирует формат ответа со строгой JSON Schema.

Вывод провайдера остаётся недоверенным, пока его не примет `validate_provider_output()`.
Содержательно пустой вывод провайдера не проходит валидацию. Некорректные необязательные
фрагменты могут превращаться в предупреждения валидации. Необработанные/очищенные
артефакты провайдера являются внутренними и не должны становиться обычным содержимым
пользовательского интерфейса или экспорта. Метаданные ссылок на них могут появляться
в перечне артефактов API; этот перечень не является интерфейсом скачивания произвольного
содержимого артефактов.

## 9. Хранение, предпросмотр, удаление и срок хранения

Локальные корневые каталоги хранилища по умолчанию:

- БД: `./data/app.db`;
- загрузки: `./data/uploads`;
- результаты: `./data/results`.

`DocumentJob` и `ExtractionAttempt` сохраняют состояние задачи, метаданные
провайдера/модели/схемы, состояние валидации, ссылки на артефакты и безопасные
метаданные ошибок. Репозитории обеспечивают переходы состояний и поведение поиска
задач/попыток.

Правила артефактов:

- Исходный загруженный файл хранится в отдельном каталоге каждой задачи.
- Необработанные/очищенные/ошибочные артефакты провайдера используют проверенные относительные пути результатов.
- Явный экспорт Markdown записывает `jobs/{job_id}/exports/result.md`.
- Абсолютные пути, префиксы дисков, переход к родительским каталогам и небезопасные сегменты пути отклоняются.

Предпросмотр / удаление / срок хранения:

- Предпросмотр проходит через `GET /jobs/{job_id}/preview` и перед выдачей проверяет, что целевой путь находится внутри корневого каталога загрузок.
- Удаление проходит через `DELETE /jobs/{job_id}` и пытается очистить связанные деревья загрузок/результатов, пропуская небезопасные структуры артефактов.
- `DocumentProcessingFacade.cleanup_expired_jobs()` существует и использует `ARTIFACT_RETENTION_DAYS`.
- Планировщик, `cron`, фоновый процесс, CLI или публичная конечная точка очистки сейчас не задокументированы как принятый механизм автоматической очистки.

## 10. Проверка результата и экспорт

Проверка результата строится из принятых данных результата извлечения, а не из
необработанных ответов провайдера. `application/result_review.py` преобразует
факты из таблиц в `review.derived_table_facts`, чтобы важные значения,
представленные внутри таблиц, можно было показать рядом с обычными полями без
слепого уплощения вывода провайдера.

Пользовательские поверхности результата/экспорта:

- рабочая область веб-интерфейса;
- JSON API результата после серверной валидации;
- экспорт Markdown;
- экспорт PDF;
- предпросмотр/скачивание исходного загруженного файла через серверную конечную точку.

Разделы экспорта Markdown/PDF по умолчанию предназначены для пользователя:
сводка, предупреждения, поля/значения, таблицы и текст. Внутренняя диагностика,
метаданные извлечения, отладочные данные провайдера/модели/задачи/попытки,
необработанный ответ провайдера, очищенный ответ провайдера, секреты, локальные пути
и URL промежуточного размещения не входят в пользовательский экспорт по умолчанию.

## 11. Поверхность веб-интерфейса

Веб-интерфейс статический и подключён по адресу `/app`. Тексты текущего интерфейса
на русском языке. Он использует относительные конечные точки серверной части и
выступает точкой доступа к возможностям, принадлежащим серверной части.

Текущие возможности:

- загрузка;
- сброс состояния выбранного файла и локальный предпросмотр изображения;
- список `Мои файлы` / история;
- рабочая область;
- серверный предпросмотр или заглушка для скачивания файла;
- представления значений, значений из таблиц, таблиц, текста и Markdown;
- копирование/скачивание Markdown;
- скачивание PDF;
- подтверждение удаления и удаление текущей задачи/элемента истории.

Основные статические файлы:

| Файл | Ответственность |

## 12. Скрипты и инструменты разработки

- `scripts/manual_provider_smoke.py` — явный ручной скрипт быстрой проверки реального провайдера.
  Он требует `RUN_REAL_PROVIDER_SMOKE=1`, `EXTRACTION_PROVIDER=openrouter`,
  `MEDIA_STAGING_BACKEND=imgbb`, включённого структурированного вывода,
  настоящих учётных данных/модели OpenRouter, настоящего ключа ImgBB и существующего
  локального пути к изображению. В выводе он скрывает чувствительные значения,
  URL и необработанный текст.

Для обычной валидации используется `uv`:

```powershell
uv run pytest
uv run ruff check .
uv run pyright
git diff --check
```

Стандартная автоматизированная валидация не должна выполнять реальные вызовы внешнего провайдера.

## 13. Тесты

Тесты сгруппированы по каталогам и назначению:

- `tests/api/` — поведение HTTP-адаптеров, отображение конечных точек и раздача статического интерфейса.
- `tests/application/` — фасад, связывание компонентов во время работы и данные проверки результата.
- `tests/contracts/` — перечисления, схемы и контракты состояний/результата.
- `tests/core/` — разбор настроек, значения по умолчанию и валидация конфигурации.
- `tests/db/` — начальная инициализация БД, репозиторий задач и жизненный цикл попыток извлечения.
- `tests/diagnostics/` — поведение детерминированной диагностики изображений.
- `tests/export/` — поведение экспорта Markdown/PDF и границы пользовательского вывода.
- `tests/extraction/` — порт провайдера, `fake`/OpenRouter, пакет промпта/схемы, границы этапов и валидация/очистка.
- `tests/media/` — порты подготовки медиа и подготовка через ImgBB с внедряемыми/фиктивными транспортами.
- `tests/providers/` — построение входного контекста провайдера.
- `tests/scripts/` — разрешающие условия, предварительные требования и скрытие чувствительных данных ручной проверки провайдера.
- `tests/services/` — приём, рабочий процесс извлечения и координация экспорта результата.
- `tests/storage/` — структура артефактов и безопасная работа с путями/удалением.

По умолчанию тесты должны оставаться детерминированными и работать без сети.

## 14. Будущие / отложенные области

Отложенные или будущие области, которые не являются текущими обязательствами MVP:

- аутентификация/учётные записи и изоляция нескольких пользователей;
- биллинг/платежи/квоты;
- промышленное развёртывание и усиление надёжности/безопасности промышленной среды;
- планировщик/`cron`/фоновая очистка по сроку хранения;
- расширенный просмотрщик/редактор или пользовательский процесс исправления;
- универсальный просмотрщик артефактов / скачивание произвольных артефактов;
- полное восстановление исходной компоновки;
- полноценный конвейер извлечения данных из PDF на входе.

Этот раздел не является списком задач; каждый пункт требует отдельного согласования перед реализацией.
